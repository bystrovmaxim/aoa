# Phase 1 Data Model: The demonstrator stand

Two halves: the stand's components (containers, front end, deploy script) and the new fixture shapes in the demo model.

## Stand components

| Component | What it is | Key attributes |
|-----------|------------|----------------|
| **Demonstrator container** | the demo service built from this repository | `[fastapi]`+`[mcp]` extras; entry point `uvicorn aoa.demo.fastapi_mcp_services.app_fastapi_service:app`; internal port 8100; healthcheck; `restart: unless-stopped` |
| **Maxitor container** | the Maxitor service with the client built from the sources | multi-stage image (Node client build → Python runtime); internal port 8101; healthcheck; `restart: unless-stopped` |
| **Front-end virtual hosts** | two entries added to the host's existing TLS terminator | one per domain (`dev.demo.aoa.run`, `dev.maxitor.aoa.run`); proxy to the loopback ports; certificates issued and renewed by the terminator's mechanism |
| **Deployment script** | the single command | gates (DNS resolve, terminator detection) → build → up → healthcheck → verify → rollback on failure; reads `/etc/aoa-stand.env` on the host |
| **Environment file** | named configuration and secrets | lives on the host outside the repository; `deploy/stand/.env.example` documents the names |
| **Recorded picture** | the acceptance evidence | DOT + SVG (generated by the client's own builders) + browser PNG, under `specs/004-demonstrator-stand/contracts/` |

## Generalization fixtures (Part 1)

A dedicated `generalization_shapes` domain; every element's description names the shape it produces.

| Fixture | Shape produced |
|---------|----------------|
| `GeneralizationParentAction` | the parent end of a `parent_action` generalization edge |
| `GeneralizationChildActionA` / `GeneralizationChildActionB` | two children — the diagram draws two inheritance arrows into one parent |
| `GeneralizationParentEntity` | the parent end of a `parent_entity` generalization edge |
| `GeneralizationChildEntity` | the child — the ERD draws the inheritance edge |

Validation rules (enforced by the framework):

- `Action` / `Entity` / `Domain` suffixes; `@meta` / `@entity` descriptions name the shape, never a business meaning.
- Child actions subclass the parent action (`parent_action` edges); the child entity subclasses the parent entity (`parent_entity` edges).
- No other relations, no lifecycle, no dependencies — the fixtures exist for the edges alone.

## Shape audit (Part 1)

`contracts/shape-coverage.md` is the audit table: every node and edge kind published by the interchange graph (from `NodeGraphCoordinator.get_available_types()`), each marked one of:

- **carried & drawn** — the demo model has an element of this kind and the diagram renders it;
- **named gap** — the kind is not carried or not drawn, and the contract says so (the specialization axis stays here until #199 lands).

## Deployment-time gates (not modeled, asserted)

- Both names resolve (DNS) — else the script refuses.
- The host's TLS terminator is detectable — else the script refuses with the missing prerequisite named.
- SSH access: either existing host key, whichever works (Clarification Q1).
