# Phase 0 Research: Entity specialization

Every decision below is either forced by the specification, settled with the maintainer (see `spec.md`, `## Clarifications`), or an engineering choice whose alternatives are named. No `NEEDS CLARIFICATION` item remains.

## D1. The field parameterises a container with the alternatives, and a marker names the classifier and the codes

- **Decision (as it stands)**: a head field is a specialization field when it parameterises a `Specialization[...]` container and its metadata carries a `Classifier(…)` marker. The alternatives and the codes are therefore named by different constructs of different kinds — a type argument and a marker — which is what keeps the list of variants from being mixed into one undifferentiated sequence. The alternatives are the container's type argument; the classifier field and the whole code set are the marker's two named arguments. An earlier opening to this decision — alternatives in `Specialization(...)` markers, the type position carrying a wrapper — was superseded later in this file, and the paragraphs below record both the measurement and what replaced it. `Specialization` marker. Its declared type is `SpecializationOne` — a value type that takes **no type argument**, because the targets come from the markers and there is no single type to put there. `Generalization` and `Inverse` occupy the extension's annotation in the same way.
- **Rationale**: the specification requires N alternative targets (FR-001), and a Python type position can hold exactly one. Every earlier attempt to express N targets in the type — a union of containers, a container with a union argument — is either resolved to the first member (the behaviour the issue records at `_first_non_optional_member`) or is not expressible. Putting the codes beside the alternatives and the targets in the markers is the form the maintainer settled (issue, decision 6), and it makes the alternative list and the code vocabulary one declaration instead of two that must be kept in step.
- **Amended while the example was written (T001)**: the classifier arrives as a marker **object**, `By("event_type")`, not as the keyword `by="event_type"` the issue proposed. A bare keyword inside `Annotated` is a `SyntaxError` — the brackets are a subscription and subscriptions take no keyword arguments — so the proposed spelling cannot be written in Python at all; `Annotated[int, By("event_type")]` parses and reads beside the other markers. The same session measured where the metadata lives in this pydantic (2.12.5), on an entity with `from __future__ import annotations` active: `model_fields[field].annotation` is the **bare inner type** — `Annotated[SpecializationOne, By("x")]` arrives as `SpecializationOne` — while the marker objects sit in `FieldInfo.metadata` as `[By('event_type')]`, in declaration order, and equally in `get_type_hints(cls, include_extras=True)`. `FieldInfo.metadata` is the source this feature reads, for two measured reasons: it is populated even while a forward reference is unresolved, and it cannot raise, whereas `get_type_hints` raises `NameError` on such a model. The bare type in the type position is itself legal: a probe against a real `@entity` class built the model, because `BaseEntity` inherits `arbitrary_types_allowed=True` from `BaseSchema`. Note the shape of the second point: neither existing reader is broken — `entity_relation_intent_resolver` guards `get_type_hints` with `hints = {}` and `entity_schema_marker_from_annotated` reads the metadata tuple — so this is a constraint the new parser must respect, not a defect it repairs.
- **A pre-existing defect found while measuring, recorded and not fixed here**: the same guard in `entity_relation_intent_resolver` degrades silently. When `get_type_hints` raises, the fallback is `field_info.annotation`, which is the bare container class with no type argument, so `_relation_container_pair` finds no target entity and the resolver returns **no relations at all** — an empty graph, not an error. It reproduces today, without any specialization, on a model carrying an unresolvable forward reference; measured: the fallback sees `<class 'Container'>` while the model's `model_fields` still read fine. This belongs in an issue of its own: the fix is to read `FieldInfo.metadata` in that resolver too, and it touches an existing module and its tests, which this feature does not own. It is not a reason to widen this capability.
- **Superseded while the work was in progress (maintainer's decision)**: the field's declared type **is** the union of
  the extension classes, and the value is the extension object itself. The earlier design — a field whose type carried no
  target and whose alternatives lived in `Specialization(...)` markers, holding a wrapper value with an id and a variant
  code — is dropped, and `SpecializationOne` with it. What was measured on real `@entity` classes before accepting the
  change: pydantic builds such a union with no warning; an object of a class the union does not list is refused with
  `ValidationError`; a bare identifier is refused too, because pydantic tries to build one of the alternatives. The last
  point is the price, stated plainly: **a reference whose row is not loaded has no representation in this field**, unlike
  the ownership containers. The gain is that the "one of these, and only these" rule is enforced by the type system, and
  that reading the field returns exactly what was written. Consequences carried through the design: the variant code is
  declared once — in the extension's own `Generalization` marker, read by the parser from the other side — so no second
  copy can drift, and the build compares nothing; `Specialization` disappears as a marker; `By` and the second form of
  `Inverse` remain.
- **Alternatives considered**: `AssociationOne[A | B]` (a union inside the container argument — Pydantic narrows it, and the runtime value still cannot say which table a row is in); `AssociationOne[A] | AssociationOne[B]` (silently keeps the first alternative today, which is the defect); a class-level `specializations = (...)` attribute beside the field (splits the declaration in two places and leaves the field's own annotation meaningless); a new field type per code (unbounded and unreadable).

## D2. (superseded) The value type is standalone, and the relation getters do not adopt it

- **Superseded by the union design (kept for the reasoning it records)**: the value type `SpecializationOne` is dropped. *Original decision*: `SpecializationOne` is a frozen value type of its own — `id`, `variant` (the variant code), `entity` (hydrated or `None`) — and does **not** inherit `BaseRelationOne`. `BaseEntity.get_foreign_keys` gets one explicit branch so the field is still reported as a relation-shaped field; the OCEL walk keeps ignoring it, because that walk already branches on `BaseRelationOne` / `BaseRelationMany` and a specialized head row is one object, not an edge in a process graph.
- **Rationale**: inheriting `BaseRelationOne` would make a specialization indistinguishable from an ownership container to every `isinstance` check in the repository, including consumers outside this package, and would place it inside the ownership compatibility matrix it is explicitly not part of (spec, Assumptions). A standalone type plus two explicit branches is the smaller lie: the declaration says what it is, and each consumer that must know says so in one line.
- **Alternatives considered**: subclassing `BaseRelationOne` (the matrix and every `isinstance` absorbs a type that does not obey them); `AssociationOne[BaseEntity]` reused as-is (the variant becomes unrepresentable, and the summary decision that the value carries both the id and the variant would need a second field to hold it); keeping the value as a plain tuple (loses the hydration contract and the explicit failure the other containers give).

## D3. The graph gets a dedicated edge kind and a dedicated field node kind

- **Superseded in part while building it**: the vertex half of this decision was dropped. A specialization adds **no** vertex — the head's field keeps the `EntityField` row it already had, which is the single field entry the diagram shows. Measured: a vertex keyed `<head qualname>:<field name>` carries exactly the column row's id, and the coordinator keys nodes by id alone, so the two cannot coexist; and a vertex would duplicate what every edge already carries.
- **Decision (edges only)**: a new wire shape. `entity_specialization` is a head→alternative edge carrying the field name, the classifier, the ordered alternatives with their codes, the cardinality, and the description; `entity_specialization_field` is the vertex the ERD renders as one row. The extension→head direction stays the existing generalization edge family, carrying the variant code in its properties.
- **Rationale**: `entity_relation` edges are `oneOf`-constrained in the checked-in JSON schema and carry exactly one `target_id`, so a N-alternative declaration cannot be a row of that shape; and the field row the ERD must show is not a scalar `entity_field` row either. Naming both kinds after what they mean keeps `_assert_no_unknown_graph_types` honest and gives the ERD a stable thing to query.
- **Alternatives considered**: reusing `entity_relation` with `relation_type = "specialization"` and `target_id` set to the first alternative (silently drops N−1 alternatives, the same defect in the graph); one `entity_relation` row per alternative (the ERD would draw N foreign-key rows — exactly what FR-024 forbids, and the store's ERD query proves it: the `fk` CTE emits **one row per edge** with no grouping by field, so N edges become N `FK -> …` rows); no edges at all, alternatives read from a node property (the store keys everything off edge tables, and the ERD's relation query is an edge query).

## D4. The extension→head direction reuses the generalization edge with `relationship="Generalization"`

- **Decision**: the extension→head edge is a `parent_*`-family generalization edge whose `relationship` is `Generalization`, and the full-graph payload therefore keeps excluding it through the predicate that is already there. The exclusion is stated as intended behaviour in a test rather than left as a coincidence.
- **Rationale**: the specification says the reverse direction is read as generalization (Assumptions), and the edge-relationship module already ships the constant and the hollow-triangle graphics for exactly this. The full-graph viewer is a system view — it strips generalization links today for that reason — and entity specialization links belong to the ERD, where they are drawn. The predicate filters the `relationship` **column**, not the edge `type`, so any edge of any table carrying that relationship disappears from the full-graph payload while an `entity_relation`-style association edge would stay; the choice of relationship is therefore the whole decision, and it needs no new predicate and no new enum value. The ERD path applies no such filter at all.
- **Alternatives considered**: `relationship="Specialization"` (also present in the enum, with the filled triangle on the specific end — the right notation only if the edge pointed head→extension, which the semantics do not); a new relationship value (a schema enum change and a new notation for no gain); letting the edges reach the full graph (an ERD-level fact rendered in a system view, and it would need a second exclusion list to be maintained).

## D5. The rules run as one global pass over the entity nodes

- **Decision**: `EntitySpecializationValidator` collects every entity node's specialization axis and runs every build rule in a single pass, called from `NodeGraphCoordinator.build()` after the per-node wiring pass and before the DAG acyclicity check. It raises `SpecializationDeclarationError` naming the class, the field and the rule.
- **Rationale**: four of the specification's rules are global by nature — one head per extension (FR-008), equal membership across the axes of one head (FR-009), mutuality and closure (FR-015, FR-016), and acyclicity (FR-018). They cannot be decided while one class is being inspected, and the coordinator's build is the only place that already holds the whole set. The lifecycle rules are validated the same way today, so the precedent exists in the codebase rather than being invented here.
- **Alternatives considered**: validating in the resolver while each field is parsed (the axis rules are all it can see, and the rest would silently not exist); validating in the graph node constructor (runs per class with no view of the others); validating at import time through `__init_subclass__` (order-dependent, and the head may be declared after its extensions).

## D6. Type compatibility of the codes is checked against the classifier's annotation

- **Decision**: the codes of one axis are compared with the resolved annotation of the classifier field. `str` accepts any non-empty string; a `Literal[...]` accepts its own members; an `Enum` subclass accepts its members' values; any other scalar type is refused at build with a named error, because no code can be proven to be a value that field can hold.
- **Rationale**: FR-005 and FR-006 ask for pairwise-distinct, non-empty codes that the classifier can actually take. Allowing an unchecked type would push a build-time guarantee to runtime, and the specification's whole point (FR-030) is that a declaration mistake fails where it is written.
- **Alternatives considered**: checking only non-emptiness (the ERD and a DDL consumer would have to re-derive compatibility); coercing codes to the classifier's type (invents a value the developer did not write); accepting any type and checking at hydration (too late — the failure would surface per row instead of per model).

## D7. (superseded) The variant is checked against the declared alternative at hydration

- **Final shape, settled with the maintainer (supersedes both earlier attempts)**: the field parameterises a container with the
  union of the alternatives, and a `Classifier(field=…, codes=Literal[…])` marker beside it names the choosing field and the whole
  code set; each extension declares its own single-member `Literal` beside its reverse container. The codes are written on both
  sides **on purpose** and the build compares them in both directions — every class declares exactly one code, every code belongs
  to a class, the sets are equal and the sizes agree — so neither copy is the authority and no drift survives the build. What was
  measured before accepting the shape: subscripting a pydantic generic produces a real class; `get_args` on that class returns
  nothing, so the union is read from `__pydantic_generic_metadata__["args"]`; a narrower parameterisation refuses the other
  alternatives; `repr` on a mutually referencing pair recurses without bound unless `entity` is excluded from it; and a piece of
  metadata that is a `Literal` survives in `FieldInfo.metadata` and reads back through `get_args`. Two designs are dropped by this
  one: the wrapper value type `SpecializationOne`, and a bare union in the type position, which could not represent a link whose
  row was not loaded.
- **Superseded by the union design (kept for the reasoning it records)**: pydantic now refuses a class the union does not list, so no framework check is needed at that point. *Original decision*: a `SpecializationOne` constructed with an `entity` whose class is not the class declared for its `variant` raises `SpecializationDeclarationError` at that moment. A branch that does not recognise the code raises `UndeclaredSpecializationVariantError` at the point of hydration.
- **Withdrawn in part**: the `UndeclaredSpecializationVariantError` half of this decision is withdrawn, and the
  exception was deleted from the framework rather than left declared-but-never-raised. The reasoning above is
  kept because it is still right about the problem; what changed is the conclusion that specialization is where
  to solve it. A code belonging to a closed set is a notion the framework does not have, and it is wanted for
  lifecycle states, role modes and edge relationships too, so it is one feature of its own — issue #203 — rather
  than a private mechanism of this axis. `SpecializationDeclarationError` is unaffected: every build rule stays.
- **Alternatives considered**: one error type for both (the two facts need different fixes); returning `None` for an undeclared code (the collapsing the specification forbids); validating in the container constructor against the head class (the container does not know its head).

## D8. Maxitor needs five registration sites per type, and one type is not enough

- **Decision**: the store registers an edge type with **own columns** (`entity_relation` is the precedent) through five sites and six edits, and a new **vertex** type through the same five:

  | Site | File:line by the `entity_relation` / `entity_field` precedent |
  | --- | --- |
  | 1. `CREATE TABLE` in `_install_database` | `duckdb_graph_resource.py:355` (edges), `:134` (vertex) |
  | 2. `_EDGE_TABLE_NAMES` — the index/truncate registry | `:505` (edges only; vertices have no such tuple) |
  | 3. the `edges` / `nodes` union view branch | `:566` (edges), `:527` (vertex) |
  | 4. the fill function **and** its dispatch line | `:916` + `:1189` (edges), `:1062` (vertex insert) |
  | 5. `known_edges` / `known_nodes` in `_assert_no_unknown_graph_types` | `:1248`, `:1202` |

  Outside the store: `list_node_types_action.py` needs the new vertex in `_DUCK_SLUG_TO_INTERCHANGE` and `NODE_TYPE_FILL_COLORS`, or the vertex renders as an unknown kind.

- **Rationale**: the issue counted five and called them "five places of the store"; the store's own structure shows five sites per **type**, and the capability adds two types — an edge carrying the alternatives and a vertex for the ERD row — because today's `entity_relation` row cannot hold N alternatives and its `oneOf` branch carries exactly one `target_id` (research D3). The count matters: `_assert_no_unknown_graph_types` raises `KeyError` on an unregistered type and aborts the **whole** load, so a missed site is not a degraded diagram but a dead system — the store's design already makes the acceptance criterion "a missing registration must be impossible to miss" true, provided every site is named.
- **Alternatives considered**: registering the edge as an empty-properties type through `simple_edge_types` (drops the codes, so the ERD cannot label the row); folding the field vertex into `EntityField` (the ERD would show the specialization as a scalar field of the head); persisting nothing and reading the axis back out of the node payload (the store's queries are edge queries, and the ERD would need a second code path).

## D8b. The ERD side is three backend changes plus one client change, and no new test infrastructure

- **Decision**: `list_entities_action.py` gains the specialization row in the `fields` CTE, the per-alternative entry in the relation query, and the new edge table in the `neighbor_clause`, so `include_neighbors=True` still pulls in the extensions one hop away. `list_entities_action_schema.py` widens the field-row contract by exactly the keys the row needs — the schema is `additionalProperties: false` and enforced at runtime, so an unplanned key is rejected before it ever reaches the browser. `client/src/lib/buildDotSource.ts` emits the relation with `arrowhead=empty style=solid penwidth=1`, the notation the use-case diagram already uses (the SVG post-pass turns the light fill into a hollow triangle). The rendering is verified by reading the generated DOT and the rendered diagram and recording both in the documentation, **not** by a new client test.
- **Rationale**: `include_neighbors` is a documented parameter whose purpose is "this entity and everything it touches"; a specialization edge missing from that clause would make the parameter quietly wrong for the one relation kind with N targets. The client change is required by the acceptance criteria — the ERD sets no arrowhead today, so Graphviz's default filled arrow says the opposite of "is a variant of". On tests: the client package has **no test runner at all** (no `test` script, no vitest or jest dependency, not one `*.test.*` file), and adding one is a piece of work with its own cost and its own decision; the repository's check run builds the client but does not test it, and the constitution's rule is that documentation shows the real output, which is what makes the rendering checkable.
- **Alternatives considered**: introducing vitest for the client (a new dependency, a new script and a new CI concern inside a feature that is not about the test runner — a separate issue); leaving `neighbor_clause` alone (one-hop expansion silently incomplete); widening the payload with a `variant` object instead of labelling the row (a browser-model change for decoration); drawing the relations without an explicit arrowhead (the diagram contradicts the model).

## D9. The ERD row carries the union type and the classifier in the existing field-row shape

- **Decision**: the specialization field appears in the ERD payload's `fields` list as one row — `name` = `<field> (by <classifier>)`, `type` = `Class (code)` per alternative — with `foreign_key = true` and no per-alternative rows.
- **Superseded in part while planning the drawing**: the relation list gains **one entry per axis**, pointing at an axis **container**, not one entry per alternative. The first form was written before the container was asked for, and the two cannot both hold: N relation lines would say N links, which is the reading the one-row field exists to prevent. The alternatives travel in a **group** the client draws around them.
- **Rationale**: the ERD's field-row contract is already `name` / `type` / `primary_key` / `foreign_key`, and the client renders exactly those four. Widening the contract would touch the browser model, the viewer and the payload schema for a label that fits in the existing one. The alternatives themselves stay reachable in full through the graph edge, which is where a consumer that needs the codes reads them (FR-022).
- **Alternatives considered**: a new `variant` field on the row (a client and payload change for decoration); one row per alternative marked `FK -> X` (the shape the acceptance criteria forbid); dropping the row entirely (the head would appear to have no continuation at all).
