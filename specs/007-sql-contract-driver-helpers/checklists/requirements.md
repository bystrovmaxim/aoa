## Notes

- **Type of feature, stated plainly**: this is an internal framework-and-library change whose "users" are the developers who build against the framework — the same reading as the specification before it. There is no end-user business flow to describe, so the vocabulary is the library's own: contract, resource, driver, helper, wrapper, nested action, unit of work. The two checklist items about "implementation details" and "non-technical stakeholders" are read in that light: no language, driver library or file path appears as a requirement, while the member shapes the issue states do, because they *are* the contract the feature changes.
- **How this specification was written**: from the issue text and from the working tree, which has moved since the issue was filed — [#215](https://github.com/bystrovmaxim/aoa/issues/215) merged as `1e4c6b02` before this branch was cut. Every site the issue names was located in the current code rather than trusted from the issue: the framework and the adapters call the removed member nowhere (verified by search over `packages/*/src`), the only use of it under `packages/` is the demo's own `identity_store_base.record_login` added by #215, and the line numbers the issue cites have drifted (`postgres_resource.py:223`, not `:136`; the PostgreSQL page was rewritten).
- **The clarification round ran and asked five questions, all answered** (`### Session 2026-10-17 — clarification` in the spec), so the earlier reading that "no clarification round is needed" no longer describes this specification. The round settled: the changelog stays under `## [Unreleased]` with no version bump (the maintainer confirmed the #215 correction over the issue's wording); the removal is a clean break with no alias and no deprecation window; the helper set is exactly the two members the issue names, with the demo's own read reshaped to a single row so both have a caller; the demo's driver-free base keeps the storage primitives and the transaction, rather than pushing both operations into each store; and the tutorial case that ran a query through the proxy is deleted with its notebook and section, its surviving half moving into the nested-action case. Every answer was applied to the requirements, the edge cases or the success criteria in the same session, and the Clarifications section carries the question and the answer for each.
- **Two of the round's answers came with a measurement that corrects the issue, and both are recorded in the spec**: (1) the issue's premise that an uncalled helper would fail the dead-code check does not hold — the repository runs `vulture` with `min_confidence = 80`, an unused method carries 60 %, and a scratch file proved it (exit 0 at 80, `unused method … (60% confidence)` at 60), so "no speculative API" is the maintainer's rule rather than something the check enforces, while the check does catch the unused `Any` import the stubs lose; (2) `fetchrow` is the same driver call as `fetch` with the protocol's row cap set to one, so it appends no `LIMIT`, shares the prepared statement and cannot be slower — its hazard is that it returns the *first* row, which is now an edge case and a documentation obligation.
- **The decisions taken while writing, each with its evidence, each recorded in Clarifications**: **(1) the demo's driver-free base keeps its own storage primitives** — a single-row read and the write beside it — so the domain keeps one transaction and the two stores implement the same pair, the PostgreSQL one through the helpers, and the in-memory one without sniffing statement text (SC-017). **(2) The stub list is two modules short**, because the issue predates #215: `identity_store_stub.py` carries the member and `identity_store_base.py` calls it. **(3) The line numbers the issue cites are not carried** — planning re-locates each site, because #215 rewrote both the driver and the PostgreSQL page after the issue was filed.
- **Coverage of the issue's own test list**: the issue names a helper on a closed resource raising the framework's error rather than an attribute error, a driver failure arriving as the framework's error rather than the driver's own type, the proxy exposing neither the removed member nor a helper, a domain wrapper delegating its own method while refusing the lifecycle, a subclass needing only `open`/`begin`/`rollback`, the contract check staying true after the shrink, and every existing check green with no live database. All are mapped to FR-025 … FR-028 and SC-002 … SC-007, SC-015, plus SC-017 for the in-memory store no longer reading statement text and SC-018 for the deleted case and the nested-action demonstration, so planning inherits the whole list rather than a summary of it.
