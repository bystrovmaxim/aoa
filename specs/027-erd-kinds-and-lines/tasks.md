# Tasks: Entity Kinds Travel with the Graph, and the ERD Shows Every Line It Should

**Input**: Design documents from `specs/027-erd-kinds-and-lines/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/ (graph-json-entity-kind, list-entity-kinds, list-entities-relations, erd-svg-postpass), quickstart.md

**Tests**: Required. pytest per package; the client's vitest files run in the check run (`npm test`), so they are fast and deterministic under jsdom; ERD drawing is checked by a plain-Node script on the client's own WASM Graphviz, wired into `scripts/run_checks_with_log.sh` like the existing `check-erd-*.ts`. The house rule is adversarial: for each new test, break the code the way the test must catch, confirm that test fails and no other does, restore, and record the break here.

**Organization**: one phase = one commit, in the order of plan.md "Phases", which follows issue #239 §12 one to one; each phase names the user stories it delivers (US1–US8 of spec.md). The three tail tasks (check run, documentation, changelog) are reserved and come last, in that order (constitution VI). Every commit is **prepared and shown**, never made without the maintainer's instruction (constitution I). Every commit message references `(#239)`.

**Issue checkboxes**: issue #239 §12 lists phases 1–9 as numbered checkboxes; commit *n* ticks box *n* (`gh issue edit 239`) once it lands. Commit 0 has no box.

**Reference graph**: `specs/025-graph-index-memory/data/ref-graph-2026-10-26.json.gz` (the admingameoffer graph, SHA-256 `a9d73e90…f84cf`).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no shared dependency)
- **[Story]**: maps the task to a user story (US1–US8)
- Every description carries an exact file path.
