Architecture diagrams usually live in Confluence or Miro and go stale faster than they are drawn: a month after release new domains appeared, steps were renamed, dependencies changed — and the diagram stayed the same. The gap between what is written and what runs is a familiar trouble.

**Maxitor** breaks this cycle: the diagrams are not drawn by hand — they are **generated by the same code that runs**. Everything you declared through intents throughout this guide (`@meta`, `@check_roles`, `@depends`, aspects, `@entity`, relations, `Lifecycle`) automatically lands in the graph. The code changes — the diagram changes; open the browser — you see the current system.

## Four projections of one system

Maxitor shows the system from four sides — and all of them are built from the same code:

| Projection | What it shows |
|------------|---------------|
| **Full graph** | everything: domains, Actions, pipeline steps, resources, dependencies, relations |
| **ERD** | entities, fields, relations, and cardinality by domain |
| **Use case** | roles and the Actions available to each role |
| **Lifecycle** | the finite-state machine of a specific entity |

This echoes [The system from different altitudes](../explanation/system-altitudes.md): Maxitor builds the first projections from code automatically.

## The full graph

The full graph is an interactive network of all the system's elements. Nodes of different types, each with its own color: **Domain** (groups Actions), **Action**, **RegularAspect/SummaryAspect** (pipeline steps), **Compensator** (saga rollbacks), **ErrorHandler**, **Resource** (`@depends`), **Entity/EntityField** (the data model), **Lifecycle**, **Role**, **Params/Result/Field** (the operation's contract). The left panel filters by group, the graph can be zoomed, a cluster isolated.

The effect is simple: a new developer understands the system's structure in five minutes without reading code, and a reviewer sees what changed without diffs across dozens of files.

## ERD, use case, and lifecycle

- **ERD** (entity–relationship diagram) is built from [`BaseEntity`](step-20-entity.md) classes and [relations](step-21-relations.md): which entities are in a domain, their fields and types, how they connect (`AssociationOne/Many`, `Aggregate…`, `Composite…`), direction and cardinality. No YAML — you write code, you get the schema.
- **Use case** is read straight from the [`@check_roles`](step-03-authorization-and-roles.md) annotations: who can call which operations. This is a ready access audit — an answer to "can a manager do this?" without opening the code.
- **Lifecycle** for each entity with a [`Lifecycle`](step-22-lifecycle.md) field draws a finite-state machine: states, transitions, initial and final vertices. Especially useful when there are a dozen statuses.

## Dictionaries in the entity diagram

An **entity–relationship diagram**, or **ERD**, describes the declared domain model.
Each table-shaped card represents an entity class; its rows describe fields. The shape
does not prove that a database table exists. `PK` and `FK` are diagram hints, not generated
database constraints.

A closed dictionary is one entity class with several declared values. In the diagram it is an
ordinary entity card: its header and its own field rows — an identifier, an obsolescence flag,
whatever the dictionary declares — and nothing more. The values it accepts are **not drawn**: no
row per value, no descriptive properties, no codes, and nothing standing in for them such as a
count. A dictionary of three values and one of ninety-three therefore look the same, which is what
keeps a real catalogue — a list of regions, say — from setting the height of the whole diagram.
The values are still in the graph and in the ERD response for anything that needs them, and the
[next section](#follow-one-property-across-the-boundary) follows a value's properties across that
boundary.
The values are not separate cards or graph nodes. A dictionary selection uses an explicit ordinary relationship, including One/Many and ownership containers. Its retained field row names the
referenced dictionary beside its type, with an arrow marker. The current payload also contains
a synthesized FK row for the same field; this duplication is a confirmed limitation, not two
separate domain fields.

The [dictionary ERD script](../../examples/step_20_dictionaries/09_erd.py) and
[notebook](../../examples/step_20_dictionaries/09_erd.ipynb) build a small currency/price
model and pass its actual graph through Maxitor's query. They print:

```text
{'code': 'eur', 'display_name': 'Euro', 'properties': [{'name': 'symbol', 'value': '€'}]}
CurrencyEnumEntity
Currency field rows: 2
Relation: currency (one) -> CurrencyEnumEntity
```

### Follow one property across the boundary

The graph is a model description. Its dictionary reference keeps properties as an object:

```json
{"code": "eur", "display_name": "Euro", "properties": {"symbol": "€"}}
```

`to_reference()` produces this data in JSON mode. Dates, Decimal values and tuples are
converted to JSON-compatible values, and a field serializer determines the exported
representation of its field. The [serializer example](../../examples/step_20_dictionaries/12_field_serializer.py)
([notebook](../../examples/step_20_dictionaries/12_field_serializer.ipynb)) demonstrates
this before any viewer is involved. Maxitor receives the saved values; it does not
reconstruct Python dictionary classes or rerun their serializers.

The ERD response serves a different purpose: it provides display rows. Its schema must
name the keys of every object, while a dictionary may declare arbitrary property names.
The server therefore turns the property object into a list with one fixed item shape:

```json
{"code": "eur", "display_name": "Euro", "properties": [{"name": "symbol", "value": "€"}]}
```

Both item fields are strings. A string property remains its text. Other JSON values are
rendered with JSON notation: `true`, `42`, `null` or `["a", "b"]`. The renderer displays
each name/value pair beneath the value's label and escapes both strings, so a note such
as `<safe> & readable` appears as text rather than diagram markup. A value with no extra
properties has `properties: []` and still shows its label and keeps its code in the tooltip.

This conversion belongs to the ERD response; the graph keeps the original properties
object. The payload also retains `entity_kind`, `values` and a referencing field's
`reference_qualname`. It requires neither a `properties_json` field nor a predefined list
of domain fields. Existing graph files that already contain the properties need no
rebuild merely to show them. A graph that omitted data cannot recover that data in the viewer.

The backend checks the response against its schema, and the client check exercises the
actual Graphviz SVG output, including escaped property text. These are different
boundaries: successful reference serialization alone does not prove that a property
survives the query and appears in the card.

## Specialization: the variants in one frame

### Read the entity diagram before interpreting its arrows

The [record model](step-21-relations.md#generalization-and-specialization) has a head,
`VinylRecordCoreEntity`, with common record information. Its first-pressing, re-pressing and
test-pressing classes contain the alternative sets of specific data. The `pressing` field
and `VinylRecordKindEnumEntity` dictionary form one **axis**: one declared choice among
those classes.

The head has one `pressing` row. It has no additional `media` selector, because the selected
value belongs to the specialization container. The ERD groups the three alternatives in a
dashed frame labelled `pressing (by VinylRecordKindEnumEntity)`. That frame represents a
choice; it is not another entity and does not mean all alternatives are loaded at once.

### Generate the diagram data from the working model

The [script](../../examples/step_21_relations/13_specialization_erd.py) and
[notebook](../../examples/step_21_relations/13_specialization_erd.ipynb) contain the complete
five-class model: dictionary, head and three alternatives. Run the script from the
repository root:

```bash
uv run python examples/step_21_relations/13_specialization_erd.py
```

It builds AOA's graph, loads the exported metadata into `DuckDBGraphResource` and asks
`ListEntitiesAction._slice_payload` for the ERD projection. This is the internal query
used by the viewer; the example uses it to inspect the diagram without starting an HTTP
service. It is not a public persistence API for application data.

Output:

```text
pressing
FirstPressSpec (first) | RepressSpec (repress) | TestPressSpec (test)
Groups: 1
Alternatives: 3
Group links: 1
Saved: examples/step_21_relations/02_specialization_erd.json
```

`entities` supplies cards, `groups` supplies visual frames and `relations` supplies drawing
connections. The type text lists class display names and their declared codes; the `Entity`
suffix is omitted in that text. The dictionary supplies alternative order, while each
alternative's marker determines its corresponding code.

### One layer owns the group label

The server builds the complete `label`; the client escapes and renders that label. There
is no separate `dictionary_label` in the ERD group payload for the client to append.
The dictionary metadata remains in the graph's specialization edges, where it describes
the model rather than prescribing display text.

The [group-label script](../../examples/step_21_relations/51_group_label.py) and
[notebook](../../examples/step_21_relations/51_group_label.ipynb) use the same record model
but inspect only this contract:

```text
Label: pressing (by VinylRecordKindEnumEntity)
Separate dictionary label: False
```

The label is `pressing (by VinylRecordKindEnumEntity)` once. The server's query still
uses graph metadata to compose it; the client does not try to reconstruct it. The
`classifier_field` compatibility member remains in the group and is normally null for
a dictionary-classified axis. No separate classifier field is added to the head entity.

### Inspect the actual rendered picture

![Record specialization rendered by Maxitor](../../examples/step_21_relations/02_specialization_erd.svg)

The dictionary card lists first, repress and test. The alternatives remain separate cards
inside the frame, so their fields—stamper, year and approved_by—remain readable. The head
sits outside that frame. Its field is summarized as `Specialization 3+`; the tooltip holds
the full mapping. Generalization arrows lead from the alternatives back to the head.
The payload's group-directed connection is a rendering instruction, not an extra object.

To regenerate the image after the Python script, use the installed client dependencies:

```bash
node examples/step_21_relations/render_specialization_erd.mjs
```

This writes the [DOT source](../../examples/step_21_relations/02_specialization_erd.dot)
and [SVG image](../../examples/step_21_relations/02_specialization_erd.svg) from the saved
[JSON payload](../../examples/step_21_relations/02_specialization_erd.json), using Maxitor's
current `buildDotSource` and Graphviz renderer. Graphviz is the program that positions the
cards and arrows; DOT is its input language.

### What happens when there is only one alternative?

A dictionary with one value can classify `Specialization[FirstPressSpecEntity, Dictionary]`.
There is a relationship, but there are no competing alternatives to enclose in a frame.
The [single-alternative script](../../examples/step_21_relations/14_specialization_single_alternative.py)
and [notebook](../../examples/step_21_relations/14_specialization_single_alternative.ipynb)
use a complete model with only that value and class. They print:

```text
Groups: 0
Relation lines: 1
```

The single relation is the reverse generalization. No multi-alternative group is created.
Similarly, filtering a multi-alternative frame down to fewer than two visible members
removes the frame from the view; it does not change the declaration.

`NoGraphEdge` on the head field suppresses the forward specialization edges needed to
build a group, while preserving the field and reverse edges. The
[focused example](../../examples/step_21_relations/12_specialization_hidden_edges.py) shows
these counts independently of rendering.

### Why the full graph looks different

The logical graph contains entity and field nodes and their declared relationships. The
ERD adds display groups to those data. The full-graph view has no ERD frames: it retains
forward `entity_specialization` associations and filters edges whose relationship is
`Generalization`, including reverse `parent_entity` edges.

These are different presentations of the same model. Neither view loads business rows,
selects a variant or validates stored data. The
[container examples](step-21-relations.md#generalization-and-specialization) explain those
separate runtime operations.

## Maxitor as an AOA application

A nice detail: Maxitor itself is written in AOA. Its backend is operations exposed through [`FastApiAdapter`](step-13-fastapi.md), and it keeps the graph as a snapshot in DuckDB:

```text
AOA code (domains, Actions, entities)
        ↓
NodeGraphCoordinator — walks all elements
        ↓
snapshot in DuckDB
        ↓
FastAPI Action → JSON endpoints
        ↓
React SPA (G6 + Graphviz WASM)
```

The diagram endpoints (`GET /api/v1/full-graph`, `…/list-entities`, `…/domain-use-case-diagram`, `…/lifecycle-finite-automaton`) are ordinary AOA operations. Their JSON can be embedded into your own portal, CI pipeline, or documentation generator. The React SPA is a separate process, and in production the static assets can be served from a CDN while the API stays next to the service.

## How to run it

```bash
# backend (FastAPI, :8000)
uv run task maxitor-api

# frontend (Vite SPA, :5173; proxies /api to :8000)
cd packages/aoa-maxitor/client && npm install && npm run dev
```

Open a source as `http://127.0.0.1:5173/?source=<graph-json URL>`: every read of the SPA carries that source. The process holds at most 50 graphs, builds at most four at once, and removes a graph unread for an hour — all three are settings, listed in the [`aoa-maxitor` package README](../../packages/aoa-maxitor/README.md).

A runnable tour of the whole request contract — two sources side by side, a cold read, `400`, `422`, `503`, an explicit reload, a failed reload, idle removal, eviction and a burst — is [02_api_graph_per_source.py](../../examples/step_26_maxitor/02_api_graph_per_source.py) and its [notebook](../../examples/step_26_maxitor/02_api_graph_per_source.ipynb).

The package dependencies are `aoa-action-machine`, `fastapi`, `uvicorn`, `duckdb`.

## Invariants

- **Diagrams are not drawn by hand.** They are generated by the same code; the code changes — the graph changes.
- **The source is intents.** Everything declared (`@meta`/`@check_roles`/`@depends`/aspects/`@entity`/relations/`Lifecycle`) automatically becomes nodes and edges.
- **The same graph as the machine's.** Maxitor displays the `NodeGraphCoordinator` graph, which is checked at startup and feeds access.
- **Four projections.** Full graph, ERD, use case, lifecycle — from one code.
- **Maxitor is AOA.** The backend is operations through `FastApiAdapter`; the JSON endpoints are embeddable.

The full list is in [Intents and invariants](../reference/intents-and-invariants.md); the terms are in the [Glossary](../reference/glossary.md).

## Summary

Maxitor shows the system as it is in the code: four projections — the full graph, ERD, use case, and lifecycle — are built from the same `NodeGraphCoordinator` graph the machine assembles from declared intents and checks at startup. The diagrams do not go stale, because no one draws them — they are the current system. And Maxitor itself is written in AOA, with its graph available as JSON endpoints.

With this the tutorial walks the whole path: an operation and its pipeline → the service layer and transports → the data model → testing → visibility of the whole system. ## Entity kinds in the graph and store

Each Entity node carries `properties.entity_kind`, identifying the role declared by its kind base: `core`, `assoc`, `detail`, `spec` or `enum`. The graph schema also admits `state`, but state classes are excluded from ordinary Entity nodes and are represented through their lifecycle instead. Maxitor loads the kind into its `entity` table and preserves it in the reconstructed node payload.

The [graph-to-store example](../../examples/step_20_entity/11_graph_kind.py) ([notebook](../../examples/step_20_entity/11_graph_kind.ipynb)) prints `graph: core` and `Maxitor store: core` for the same order. A graph produced before this required property was added must be regenerated. Class renames also change labels and identifiers containing qualified Python names.

This makes the domain distinction available to consumers. It does not yet change the renderer: associative entities are not automatically hidden or replaced by direct edges. Such a presentation can safely rely on `assoc` only because that kind means a technical link without business data; a supplier offer with price and terms is a core object and must retain its own representation.

## Follow a dictionary reference

Declare a catalogue selection as a complete ordinary relationship field. All six containers support dictionary targets; use NoInverse for an unpaired link. Newly built graphs retain its field row and emit an ordinary `entity_relation` with the declared association/aggregation/composition family and One/Many cardinality. Older graph imports may still contain special reference edges. Rebuild older exports after migrating the declaration.

The current ERD query reads the ordinary association and displays the dictionary values. It does not yet merge the retained field row with its synthesized FK row. A single declared dictionary field therefore produces two payload rows. Consumers must not assume one row per field yet; see the [reproduction and required correction](../reports/complete-relationship-verification.md#dictionary-fields-in-maxitor). No client rendering or full application compatibility claim is made by this backend payload example.

See [selection declarations and transport](../how-to/dictionary-references.md), the [ERD script](../../examples/step_20_dictionaries/09_erd.py) and [executed notebook](../../examples/step_20_dictionaries/09_erd.ipynb).

The [all-container dictionary example](../../examples/step_21_relations/72_role_dictionary.py) and [notebook](../../examples/step_21_relations/72_role_dictionary.ipynb) assert the source graph for all six ordinary roles. The [current consumer reproduction](../reports/endpoint-role-verification.md#dictionary-field-rows-in-the-erd) confirms that Maxitor carries all three families but still returns two payload rows for each retained dictionary field.
